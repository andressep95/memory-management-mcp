# Commit Skill — Always Loaded

## Critical Rules

- **Standard:** ALWAYS use `type(scope): description`.
- **Anonymity:** NEVER add AI signatures, co-authors, or "Generated by" lines.
- **Tone:** English, imperative mood (e.g., "Add feature" not "Added feature"), no trailing period.
- **Length:** First line < 72 characters. Body wrapped at 72 characters.
- **Confirmation:** ALWAYS show the message to the user and ask for confirmation before executing `git commit`.
- **Isolation:** NEVER use `git push --force`.
- **Complete History:** Stage ALL modified and untracked files by default (`git add -A`). Every change must be committed to maintain a faithful project history. Never silently leave files unstaged.
- **Sensitive File Guard:** Before staging, scan for files that should NOT be committed (`.env`, `*.key`, `*.pem`, credentials, secrets). Warn the user if any are found and exclude them explicitly.
- **Granularity:** If the diff spans clearly unrelated concerns, propose splitting into two commits. If the user confirms one commit, proceed with all changes in a single commit.

## Commit Format

```text
type(scope): concise description in imperative mood

what: <one sentence — what the code does now that it didn't before>
why:  <one sentence — why the change was necessary>
breaking: <true|false>
```

`what` and `why` are **required** for `feat`, `fix`, `refactor`, `perf`, and `sec`.
They feed the RAG memory system — empty fields produce useless embeddings.
For `chore`, `docs`, `test`, `ci`, and `style` they are optional.

## Types

| Type       | Intent                                                          |
| :--------- | :-------------------------------------------------------------- |
| `feat`     | New capability, feature, or public API.                         |
| `fix`      | Bug fix or error handling correction.                           |
| `refactor` | Code change that neither fixes a bug nor adds a feature.        |
| `perf`     | Code change that improves performance.                          |
| `sec`      | Security hardening, vulnerability fixes, or permission changes. |
| `test`     | Adding missing tests or correcting existing tests.              |
| `docs`     | Documentation only (Markdown, Javadoc, comments).               |
| `chore`    | Build process, auxiliary tools, dependencies, or config.        |
| `ci`       | Changes to CI/CD pipelines and scripts.                         |

## Dynamic Scope Resolution

Resolve `(scope)` using priority:

1. **Project Module:** Top-level directory or module name.
2. **Architecture Layer:** `domain`, `infra`, `api`, `repo`.
3. **Skill/Tooling:** `skills`, `agent`, `memory`.
4. **Dependency:** `deps` for package manager changes.
5. **Cross-Cutting:** `global` or `core` if system-wide.

## Workflow

1. `git status` + `git diff --stat HEAD`
2. Scan for sensitive files — warn and exclude.
3. If unrelated concerns, propose split. If user says one commit, proceed.
4. Check style: `git log -3 --oneline`
5. Present draft → confirm → stage and commit:
   ```bash
   git add -A
   git commit -m "$(cat <<'EOF'
   type(scope): description

   what: what the code does now
   why: why it was necessary
   breaking: false
   EOF
   )"
   ```

## Rules for `what` and `why`

- One sentence each
- `what`: the new behavior — not the file, not the task
- `why`: the motivation — most important field for semantic search
- ❌ `what: fix bug` / `why: it was broken`
- ✅ `what: Replaces individual queries with batch fetch in getUserList`
- ✅ `why: Previous version made N DB roundtrips per user, O(n) instead of O(1)`
